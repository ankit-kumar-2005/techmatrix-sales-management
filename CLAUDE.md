# Techmatrix Sales Management — Engineering Rulebook

This document is the primary engineering rulebook for this repository. It governs how Claude
Code (and any engineer working alongside it) plans, builds, reviews, and ships this project.
When in doubt, this file wins over ad-hoc convention.

## A. Project Overview

**Purpose.** Techmatrix Sales Management is an enterprise sales management application. It
gives sales teams a single system for capturing leads, tracking them through a pipeline,
managing contacts and tasks, forecasting revenue, running automations, and reporting on team
performance.

**Main modules** (as reflected in the UI):

- Pipeline — visual/kanban view of deals moving through sales stages
- Lead Capture — intake and qualification of new leads
- Automations — rule-based workflows triggered by lead/deal/task events
- Catalog — products/services that can be attached to opportunities
- Contacts — people and organizations associated with leads/deals
- Tasks — follow-ups, reminders, and action items tied to leads/deals/contacts
- Team — user and team management within an organization
- Forecast — revenue projection and pipeline analytics
- Meeting Notes — structured notes attached to leads/contacts/opportunities
- Settings — organization, user, and application configuration

**Multi-tenant architecture.** The application serves multiple independent organizations
("tenants") from a single deployment and a single database. Every organization's data —
leads, contacts, tasks, opportunities, catalog items, meeting notes — must be fully isolated
from every other organization's data. Multi-tenancy is a cross-cutting concern that touches
the database schema, RLS policies, API/service code, and UI data-fetching. See
[Section G](#g-multi-tenant-security) and the `multi-tenant-security` skill — treat both as
required reading before touching any data-access code.

**Expected user roles**, scoped per-organization (a user's role can differ across
organizations if the platform ever supports multi-org membership):

- **Admin** — full control over the organization: users, roles, settings, billing, all data
- **Manager** — manages a team's pipeline, leads, forecasts; broader visibility than a
  Salesperson but not full org administration
- **Salesperson** — manages their own leads/contacts/tasks/opportunities; limited visibility
  into other salespeople's records unless explicitly shared

**Future React Native / Expo application.** The backend (Supabase, PostgreSQL, RLS,
service-layer logic, and any Route Handlers that exist for cross-client needs) must remain
usable by a future mobile client, not just this Next.js app. Practical implications:

- Business logic and authorization rules belong in the **database (RLS)** and **service
  layer**, not scattered inside Next.js UI components or Server Actions only — a mobile app
  cannot call a Server Action.
- Anything a mobile client will need (auth flows, data mutations, business rules) should be
  reachable through Supabase directly (with RLS enforcing security) or through Route Handlers
  that expose a real API — not exclusively through Next.js-only mechanisms.
- This does not mean "build the mobile API now." It means: when choosing between logic living
  only in a Server Action vs. living in a service function callable from a Route Handler too,
  prefer the latter once the project reaches backend phases.

## B. Technology Stack

For each technology: what it's for, when to reach for it, when not to, and the conventions
this project follows.

### Frontend

**Next.js (App Router)**
- Use for: routing, layouts, Server/Client Component composition, Route Handlers, Server
  Actions, metadata, streaming/loading UI.
- Don't use for: anything that belongs in the database (authorization, tenant isolation) —
  Next.js is a delivery layer, not the security boundary.
- Convention: App Router only. No Pages Router. Server Components by default (see
  [Section D](#d-nextjs-architecture-rules)).

**React**
- Use for: UI composition and interactivity.
- Don't use for: data fetching that could happen on the server, or business logic that
  belongs in a service module.
- Convention: function components, hooks, no class components.

**TypeScript**
- Use for: all application code. No `.js`/`.jsx` files in app code.
- Convention: `strict` mode stays on (already enabled in `tsconfig.json`). See
  [Section L](#l-typescript-rules).

**Tailwind CSS**
- Use for: all styling. Utility-first, no separate CSS files per component beyond
  `app/globals.css` for tokens/resets.
- Don't use for: one-off styling that would be clearer as a shared shadcn/ui variant — prefer
  extending the component over piling on ad-hoc utility classes at every call site.

**shadcn/ui**
- Use for: base UI primitives (button, dialog, table, form controls, etc.), copied into
  `components/ui/` and owned by this repo (shadcn is not a runtime dependency — it's a
  generator).
- Don't use for: feature-specific composite components — those belong under `features/*/`.
- Convention: don't hand-edit generated primitives beyond what's needed to fit the design
  system; if a primitive needs heavy customization, wrap it rather than forking its internals
  repeatedly.

### Backend

**Next.js Route Handlers (`app/api/**/route.ts`)**
- Use for: endpoints that need to be callable outside of a React render — webhooks, endpoints
  the future mobile app will call, third-party integrations, file exports.
- Don't use for: business logic itself — handlers stay thin and delegate to `services/`. See
  [Section I](#i-apibackend-architecture).

**Server Actions**
- Use for: form mutations initiated from this Next.js app's own UI, where a dedicated REST
  endpoint isn't otherwise needed.
- Don't use for: logic that the future mobile app will also need to trigger — put that behind
  a service function callable from a Route Handler instead, and optionally have the Server
  Action call the same service.
- Convention: Server Actions validate input with Zod and delegate to the service layer, same
  as Route Handlers do — they are not a shortcut around validation/authorization.

**Service layer (`services/`)**
- Use for: business/domain operations — the actual "create a lead," "move opportunity stage,"
  "assign task" logic, including authorization checks that go beyond RLS.
- Don't use for: HTTP concerns (status codes, request parsing) — that's the Route Handler's
  job — or UI concerns.

### Database

**Supabase**
- Use for: Postgres hosting, Auth, RLS-backed data access, storage (when needed).
- Don't use for: bypassing RLS from client code "just this once" — see
  [Section E](#e-supabase-architecture).

**PostgreSQL**
- Use for: the single source of truth for all persistent data.
- Convention: schema changes via migrations only. See
  [Section F](#f-database-engineering-rules).

**Row Level Security (RLS)**
- Use for: enforcing tenant isolation and role-based data access at the database level — the
  last line of defense, not an optional extra.
- Don't use for: the *only* line of defense — pair with server-side authorization. See
  [Section G](#g-multi-tenant-security).

### Supporting libraries

**TanStack Query**
- Use for: client-side data fetching/caching when a Server Component fetch isn't sufficient
  (e.g., interactive tables with client-driven filters/pagination, optimistic updates).
- Don't use for: data that a Server Component could fetch once and pass down — don't build a
  client-fetch waterfall for data available at render time.

**TanStack Table**
- Use for: the Leads/Contacts/Opportunities tables — sorting, filtering, column visibility,
  pagination UI state.
- Don't use for: rendering the actual pagination/filtering/sorting *logic* — that should be
  pushed to the database query, not done client-side over a full dataset. See
  [Section O](#o-performance).

**React Hook Form**
- Use for: all non-trivial forms (lead capture, contact forms, settings).
- Convention: pair with a Zod resolver so client validation and server validation share the
  same schema shape.

**Zod**
- Use for: all input validation — form schemas, Route Handler/Server Action input, and where
  useful, parsing external data (CSV imports, webhook payloads).
- Convention: co-locate a feature's schema so both client (RHF resolver) and server
  (Route Handler/Server Action/service) import the same schema. See
  [Section J](#j-validation).

**Recharts / Tremor**
- Use for: Forecast dashboards, pipeline analytics, reporting charts.
- Don't use for: large raw data tables — that's TanStack Table's job.

**PapaParse**
- Use for: CSV import/export (e.g., bulk lead import, exporting a filtered lead list).
- Convention: parse untrusted CSV input defensively and re-validate every row through Zod
  before it touches the database — never trust a CSV row as pre-validated.

## C. Project Architecture

Feature-based, scalable structure. **Do not create every directory up front** — introduce a
directory only when a real need for it exists. This is the conceptual map for where things go
once they exist:

```
app/            Routing, pages, layouts, Route Handlers — Next.js App Router conventions
components/     Shared UI: components/ui (shadcn primitives), components/shared (cross-feature)
features/       Feature-specific code: features/<feature>/components, hooks, schemas, etc.
lib/            Infrastructure/configuration: supabase clients, query client setup, constants
services/       Business/domain operations — the service layer described in Section B/I
types/          Shared/domain TypeScript types (e.g., generated Supabase DB types, domain models)
hooks/          Reusable React hooks not specific to one feature
utils/          Generic, side-effect-free helper functions (formatting, math, string utils)
config/         Application configuration (feature flags, role/permission maps, constants)
supabase/       Migrations and other database-related files (Supabase CLI project files)
```

Guidance for each:

- **`app/`** — routing, pages, layouts, `loading.tsx`/`error.tsx`/`not-found.tsx`, route
  groups, Route Handlers. Keep it thin: pages compose components and call services; they
  don't contain business logic.
- **`components/`** — UI with no feature-specific business meaning. `components/ui/` for
  shadcn primitives, `components/shared/` for things genuinely used by 2+ features (a page
  header, an empty-state block, etc.).
- **`features/`** — everything specific to one module (Leads, Contacts, Pipeline, ...):
  components, hooks, Zod schemas, feature-local types. A feature should be deletable without
  breaking unrelated features.
- **`lib/`** — infrastructure and setup code: Supabase client factories, the TanStack Query
  client, third-party SDK setup. Not business logic.
- **`services/`** — the domain/business layer. Route Handlers and Server Actions call into
  here; here is where authorization and cross-entity rules live alongside RLS.
- **`types/`** — types shared across features/layers, notably generated Supabase database
  types and hand-written domain types built on top of them.
- **`hooks/`** — React hooks reused across features (e.g., `useDebouncedValue`). Feature-only
  hooks stay inside that feature's folder instead.
- **`utils/`** — pure helper functions with no framework/React dependency.
- **`config/`** — static application configuration, e.g., a role → permission map.
- **`supabase/`** — migrations, seed files, and Supabase CLI configuration once Supabase is
  connected (not yet, per current phase).

## D. Next.js Architecture Rules

- **Server Components by default.** Every component starts as a Server Component. Add
  `"use client"` only when the component needs interactivity, browser-only APIs, state, or
  effects that genuinely require the client.
- **Don't make entire pages Client Components** to work around one interactive widget — push
  `"use client"` down to the smallest leaf component that actually needs it, and pass server-
  fetched data into it as props.
- **Keep server-only code out of the client bundle.** Never import server-only modules (e.g.,
  a Supabase server client, anything touching `SUPABASE_SERVICE_ROLE_KEY`, filesystem/Node
  APIs) from a file that is or could be pulled into a Client Component's module graph. Use the
  `server-only` boundary conceptually even before formal enforcement is wired up.
- **Never expose secrets to client code.** No secret, service-role key, or non-`NEXT_PUBLIC_`
  environment variable may be referenced from a Client Component, a client-imported module, or
  inlined into client-rendered HTML.
- **Keep business logic out of UI components.** Pages and components call services (directly
  in Server Components, or via Route Handlers/Server Actions); they don't reimplement domain
  rules inline.
- **Layouts** hold structure shared across a route subtree (nav, shell chrome) — not page-
  specific data fetching.
- **`loading.tsx`** provides a route-level Suspense fallback for genuinely async segments;
  don't add one to routes with no meaningful async boundary.
- **`error.tsx`** is a Client Component boundary for recoverable render/data errors in a
  segment — use it to show a real recovery UI, not just a generic message, where practical.
- **`not-found.tsx`** for legitimate "this resource doesn't exist" cases (e.g., a lead ID that
  doesn't resolve), triggered via `notFound()`, not for auth/permission failures — those are
  authorization errors (see [Section H](#h-authentication-and-authorization) /
  [K](#k-error-handling)), not "not found."
- **Route groups** (`(group)`) organize routes without affecting the URL — use them to
  separate e.g. authenticated app routes from marketing/auth routes, not as a general-purpose
  organizing device.
- **Dynamic routes** (`[id]`, `[...slug]`) — validate and authorize the resolved identifier
  server-side before rendering; never assume a dynamic segment is safe or belongs to the
  current user/org just because it was present in the URL.

## E. Supabase Architecture

*(Setup happens in a later phase — this section defines the standard for when it does.)*

- **`lib/supabase/client.ts`** — the **browser** Supabase client, built with the anon/public
  key. Used from Client Components and client-side hooks. Relies on RLS for every query it
  makes; it must never be trusted to enforce authorization on its own.
- **`lib/supabase/server.ts`** — the **server** Supabase client, used from Server Components,
  Route Handlers, Server Actions, and the service layer. Reads the user's session from
  cookies so RLS still applies per-request as that user — this is not the service-role client.
- A **service-role client**, if ever needed (e.g., trusted background jobs, admin tooling),
  is a distinct, explicitly-named client, constructed only in server-only code, used only
  where RLS genuinely cannot express the operation, and never reused as the default server
  client.

**Hard rules:**

- **`SUPABASE_SERVICE_ROLE_KEY` must never be exposed to browser code** — not in a Client
  Component, not in client-bundled modules, not logged, not returned in any API response.
- **Never place service-role or other secret credentials in `NEXT_PUBLIC_*` variables.**
  `NEXT_PUBLIC_*` is inlined into the client bundle at build time and is public by
  definition — only the anon key and other genuinely public values belong there.
- **Server/client boundary:** if a piece of code decides *what data a user is allowed to see
  or change*, it either runs server-side behind the server Supabase client (with RLS active)
  or is itself enforced by an RLS policy. The browser client and any Client Component are
  untrusted input as far as authorization is concerned.

## F. Database Engineering Rules

- **Primary keys:** UUID (`uuid`, default `gen_random_uuid()` or `uuid_generate_v4()`), not
  serial integers, for anything that could be referenced across systems (including a future
  mobile client) or where PK enumerability is a concern.
- **Foreign keys:** every relationship is a real FK constraint, not just an application-level
  convention. Cascade behavior (`ON DELETE`) chosen deliberately per relationship, not
  defaulted blindly.
- **`NOT NULL`** on every column that must always have a value — don't default to nullable.
- **`CHECK` constraints** for invariants the database can enforce (e.g., an enum-like status
  column, non-negative amounts).
- **`UNIQUE` constraints** for natural uniqueness (e.g., one membership row per user per
  organization), not just enforced in application code.
- **Indexes** on foreign keys, on columns used in common `WHERE`/`ORDER BY` clauses (notably
  `organization_id` and any filter/sort columns the Leads table will use), and on anything
  RLS policies filter on — an RLS policy that isn't backed by an index silently becomes a
  full scan.
- **`created_at` / `updated_at`** (`timestamptz`, default `now()`) on every table that
  represents a mutable business entity. `updated_at` kept current via trigger, not by
  convention alone.
- **Relationships** modeled properly (join tables for many-to-many, not comma-separated IDs
  or ad-hoc arrays standing in for a real relationship).
- **Avoid unnecessary duplication** — don't copy a value across tables when a join/FK will do;
  denormalize only for a measured, specific performance reason, documented at the point of
  denormalization.
- **Avoid unnecessary JSON/JSONB fields** — prefer real columns and relationships for anything
  that will be queried, filtered, sorted, or constrained. JSONB is for genuinely
  schema-flexible data (e.g., a free-form automation config blob), not a shortcut around
  modeling.
- **Migrations only.** All schema changes are version-controlled migration files (Supabase
  CLI migrations once Supabase is connected). No manual/ad-hoc changes to any shared
  database, ever — production or shared staging.

## G. Multi-Tenant Security

**This is one of the highest-priority rules in this document.** Read alongside the
`multi-tenant-security` skill, which should be treated as required reading whenever database
access, authorization, RLS, `organization_id`, or user roles are involved.

Conceptual model:

```
Organization
    |
    ├── Users (via organization membership)
    ├── Leads
    ├── Contacts
    ├── Tasks
    └── Opportunities
```

- Tenant-owned tables carry an `organization_id` (or equivalent) foreign key wherever the row
  conceptually belongs to one organization.
- **The system must guarantee that Organization A can never access Organization B's data —
  under any circumstance, including bugs elsewhere in the stack.**
- **Never rely on frontend filtering alone.** A `WHERE organization_id = ...` clause added
  only in a client-side query, with nothing enforcing it server-side, is not tenant
  isolation — it's a suggestion an attacker can ignore.
- Tenant isolation is enforced through the combination of:
  - PostgreSQL constraints and schema design (`organization_id` present and non-null where
    required, proper FKs)
  - Supabase RLS policies scoping every tenant-owned table to the caller's organization(s)
  - Server-side authorization (service layer / Route Handlers confirming the acting user
    belongs to the organization they're operating on)
  - Application-level authorization for anything RLS can't fully express (e.g., role-specific
    field-level rules)
- **Any change that touches database access, permissions, or `organization_id` must
  explicitly consider tenant isolation** as part of planning and review — this is a standing
  item on the [code review checklist](#s-code-review-checklist), not something to reason
  about only when it's the main point of the change.

## H. Authentication and Authorization

- **Authentication** answers "who is the user?" — handled by Supabase Auth (session
  issuance, login/logout, session refresh).
- **Authorization** answers "what is this user allowed to do?" — handled by a combination of
  role/permission checks and RLS, evaluated *after* authentication, on every operation.

**Roles:** Admin, Manager, Salesperson (see [Section A](#a-project-overview) for scope of
each). Roles are per-organization membership, not a single global attribute of a user.

Standards, to be implemented in the auth/authz phases (see
[Section 7 — Phase-Based Development](#7-phase-based-development)):

- **Login/logout** go through Supabase Auth — no parallel/custom auth mechanism.
- **Session handling** uses Supabase's server-side session utilities so Server Components,
  Route Handlers, and Server Actions all see a consistent, current session — never trust a
  client-supplied user ID or role.
- **Protected routes** verify a valid session server-side before rendering protected content
  or executing protected mutations — not just hiding UI client-side.
- **Organization membership** is checked on every operation that reads/writes tenant data —
  a valid session proves identity, not which organization(s) or role the user currently acts
  under.
- **Role checks / permission checks** live in the service layer (and, where expressible, in
  RLS) — not only as conditional UI rendering.
- **RLS** is the database-level backstop for both tenant isolation and role-based data access;
  it must hold even if a server-side check is ever missed, and server-side checks must hold
  even if a policy is ever misconfigured — defense in depth, not either/or.

**Never rely on frontend role checks for security.** Hiding a button from a Salesperson is a
UX nicety; it is not authorization. Every privileged operation must be re-checked server-side
and by RLS.

## I. API / Backend Architecture

Preferred backend flow for any request that changes or reads protected data:

```
Request
   ↓
Authentication   (who is calling — Supabase session)
   ↓
Authorization    (are they allowed to do this — role/org checks + RLS)
   ↓
Validation       (is the input well-formed — Zod)
   ↓
Service          (the actual business operation)
   ↓
Database         (Postgres, behind RLS)
   ↓
Response
```

- **Route Handlers stay thin.** `app/api/**/route.ts` parses the request, authenticates,
  validates input, calls a service function, and maps the result to an HTTP response. It does
  not contain the business logic itself.
- **Business logic lives in `services/`** (or a feature's own service module), callable from
  Route Handlers, Server Actions, and (later) background jobs alike.
- **Consistent API responses** — a single, predictable shape for success and error payloads
  across all Route Handlers (exact shape to be defined when the first Route Handler is built,
  and then followed everywhere).
- **Appropriate HTTP status codes** — `400` validation, `401` unauthenticated, `403`
  unauthorized, `404` not found, `409` conflict, `500` unexpected — chosen deliberately, not
  defaulted to `200`/`500` for everything.

## J. Validation

- **Zod** is the validation library for all application-level validation.
- Validation happens at multiple, independent layers — each one matters for a different
  reason, and none substitutes for another:
  1. **Client-side** — user experience (immediate feedback via React Hook Form + Zod
     resolver). Convenience, not security.
  2. **Server-side** — security (Route Handlers, Server Actions, and services re-validate
     with the same or a stricter schema; client validation is never trusted as sufficient).
  3. **Database** — data integrity (constraints from [Section F](#f-database-engineering-rules)
     as the final backstop, catching anything application code got wrong).
- **Never trust client input** — not the shape, not the values, not the implied
  authorization (e.g., an `organization_id` or `role` field submitted by the client is never
  taken at face value; it's derived server-side from the authenticated session).
- Prefer sharing one Zod schema between client and server for a given form/operation instead
  of maintaining two schemas that can drift apart.

## K. Error Handling

Standards by category:

- **Validation errors** — return field-level details useful for the client to fix input
  (from Zod's issue list); `400`.
- **Authentication errors** — no session / expired session; `401`; generic message, no detail
  about *why* auth failed beyond "not authenticated."
- **Authorization errors** — authenticated but not permitted; `403`; message states the
  action was denied, not the internal reason (e.g., not "you're not an Admin," just "you
  don't have permission to do this" unless surfacing the role requirement is intentional
  product UX).
- **Not found errors** — resource genuinely doesn't exist *or* the user isn't allowed to know
  it exists; `404` (prefer `404` over `403` when existence itself is sensitive, e.g., another
  org's lead ID).
- **Database errors** — never surface raw Postgres error text (constraint names, internal
  schema detail) to the end user; log it server-side, return a generic `500` (or a mapped
  `409`/`400` for known constraint violations like uniqueness).
- **Unexpected errors** — caught at the boundary (Route Handler / Server Action / error
  boundary), logged with enough context to debug, generic message returned to the user.

**Never expose internal implementation details or secrets** (stack traces, query text,
internal IDs beyond what's needed, environment info) in user-facing error output.

**Consistent error structures** across the API — same shape used everywhere Route Handlers
return errors, so clients (including the future mobile app) can handle them generically.

**Log useful debugging information without exposing sensitive information** — log enough to
diagnose (request context, error, relevant non-sensitive IDs) and never log the things listed
in [Section P](#p-security).

## L. TypeScript Rules

- **Strict mode stays on** (already configured in `tsconfig.json`) — do not weaken it.
- **Avoid `any`.** If a type is genuinely unknown, use `unknown` and narrow it. `any` is a
  last resort with a reason, not a default escape hatch.
- **Prefer explicit types at boundaries** — function signatures for services, Route Handler
  inputs/outputs, and shared types are explicitly typed, even where inference could technically
  fill in.
- **Avoid unnecessary type assertions (`as`).** An assertion is a claim you're overriding the
  compiler; use it only when you genuinely know more than TypeScript can infer, not to silence
  an error you haven't understood.
- **Keep database types synchronized** — once Supabase is connected, generated DB types
  (`types/`) are regenerated whenever the schema changes; hand-written types don't drift from
  the real schema.
- **Prefer reusable domain types** over redefining the same shape per feature — a `Lead` type
  lives in one place and is imported, not restated.
- **Discriminated unions** where a value can meaningfully be one of several distinct shapes
  (e.g., automation trigger types, task statuses with different payloads) instead of one
  loose type with a lot of optional fields.
- **Don't duplicate types unnecessarily** — derive/reuse (`Pick`, `Omit`, `z.infer<...>` from
  a Zod schema) instead of hand-copying a shape.

## M. Component Architecture

```
components/ui/            Generic UI primitives (shadcn/ui components)
components/shared/         Components genuinely shared across multiple features
features/*/components/     Components belonging to one specific feature
```

- **`components/ui/`** — shadcn primitives (Button, Dialog, Table, Input, etc.). Generic,
  no domain knowledge of leads/contacts/etc.
- **`components/shared/`** — composed components used by two or more features (e.g., a page
  header pattern, an empty-state block, a confirmation dialog). Something used by exactly one
  feature does not belong here.
- **`features/*/components/`** — everything specific to one feature/module (e.g., a
  `LeadStatusBadge`, a `PipelineStageColumn`). Default location for new components — promote
  to `components/shared/` only once a real second consumer exists, not speculatively.

Do not put feature-specific components into global `components/` "just in case" — that's how
shared component folders rot. Start local, promote when actually reused.

## N. Data Fetching

- **Server Components** — default for initial page data. Fetch directly in the Server
  Component (via the service layer / server Supabase client) whenever the data is needed for
  first render and doesn't need client-side interactivity beyond what server-rendered HTML
  plus light client components can provide.
- **TanStack Query** — for client-driven data needs: interactive table filtering/sorting/
  pagination that re-fetches, optimistic updates, polling, or data that depends on client-only
  state. Seed it from server-fetched data where practical instead of double-fetching on
  mount.
- **Route Handlers** — for data the future mobile app needs, for webhooks, or for
  browser-triggered operations that don't fit a Server Action (e.g., a CSV export download).
- **Server Actions** — for this app's own form mutations where no separate REST surface is
  otherwise needed.
- **Don't create unnecessary API layers** — a Server Component doesn't need to call a Route
  Handler on the same app just to get data it could fetch directly through the service layer.
- **Don't fetch everything into the browser.** For large datasets — Leads chief among them —
  pagination, filtering, sorting, and search happen at the database/query level, not by
  loading the full table client-side and slicing it in JavaScript. See
  [Section O](#o-performance).

## O. Performance

- **Server Components** for anything that doesn't need client interactivity — less JS
  shipped, faster first paint.
- **Database indexes** on every column used for filtering/sorting/joining in a hot path
  (see [Section F](#f-database-engineering-rules)).
- **Pagination** on every list endpoint/query that could return an unbounded number of rows —
  cursor- or offset-based, decided per use case, but never "return everything."
- **Filtering and sorting** pushed to the database query (`WHERE`/`ORDER BY`), not done in
  application code after fetching more rows than needed.
- **Lazy loading / dynamic imports** for heavy, rarely-needed UI (large charts, rich text
  editors, CSV import dialogs) instead of bundling them into the initial page load.
- **Image optimization** via `next/image` for any real image assets.
- **Avoid unnecessary re-renders** — memoize where it measurably matters, keep client state
  as local as possible, don't lift state higher than it needs to be.
- **Large tables (TanStack Table)** — the Leads table may eventually contain thousands of
  records. **Never design assuming all records can be loaded into the browser at once.**
  Server-side pagination/filtering/sorting feeding TanStack Table is the standard, not an
  optimization to add later.

## P. Security

- **Authentication / Authorization** — per [Sections G](#g-multi-tenant-security)–
  [H](#h-authentication-and-authorization): server-enforced, RLS-backed, never frontend-only.
- **RLS** — every tenant-owned and role-sensitive table has policies covering `select`,
  `insert`, `update`, `delete` as applicable; a new table without RLS considered is a bug.
- **Tenant isolation** — see [Section G](#g-multi-tenant-security); this is non-negotiable.
- **Input validation** — Zod on every external input, server-side, always (see
  [Section J](#j-validation)).
- **XSS prevention** — no `dangerouslySetInnerHTML` with unsanitized content; React's default
  escaping is the norm, not the exception.
- **SQL injection prevention** — use the Supabase client / parameterized queries exclusively;
  no hand-built SQL string concatenation with user input, ever.
- **Secret management** — secrets live in environment variables, never committed, never
  logged, never sent to the client (see [Sections E](#e-supabase-architecture) and
  [R](#r-git-rules)).
- **Secure cookies/session handling** — session cookies handled via Supabase's supported
  server-side helpers, not hand-rolled cookie parsing/signing.
- **Sensitive logging** — see the list below; if unsure whether something is sensitive, treat
  it as sensitive.

**Never log:**

- Passwords
- Access tokens
- Refresh tokens
- Service-role keys
- API secrets
- Sensitive personal information (beyond what's operationally necessary, and even then,
  minimized)

## Q. Testing

- **Unit tests** — pure functions in `utils/`, `services/` logic that doesn't require a live
  database (or runs against a test database).
- **Component tests** — components with real behavior/logic worth verifying (not every
  presentational component needs one).
- **Service tests** — the domain/business logic in `services/`, including authorization
  branches.
- **API tests** — Route Handlers: status codes, validation errors, auth/authz failures.
- **Integration tests** — flows that cross layers (e.g., create-lead end to end through
  service + database).
- **Authentication tests** — login/logout/session behavior.
- **Authorization tests** — role-based access, including negative cases (a Salesperson
  correctly denied a Manager-only action).
- **RLS tests** — direct tests against policies confirming Organization A truly cannot read/
  write Organization B's rows, for every tenant-owned table.
- **End-to-end tests** — critical user journeys (e.g., capture a lead → move through pipeline
  → convert).

Testing is introduced **incrementally with features**, not retrofitted as a separate phase —
when a feature reaches an implementation phase, its relevant tests are part of that phase (see
[Section Q](#q-testing) applied per [Phase-Based Development](#7-phase-based-development)).

## R. Git Rules

- **Small, focused commits** — one logical change per commit.
- **Meaningful commit messages** — explain *what* and *why*, not just "update files."
- **Never commit `.env.local`** or any file containing real secrets/credentials.
- **Never commit secrets** in code, config, or comments — including temporarily "for testing."
- **Review changes before committing** — check `git status`/`git diff` for anything
  unintended before staging, including files that look innocuous but might carry secrets.
- **Avoid unrelated refactoring** inside a feature/fix commit — separate cleanup from
  behavior change.
- **Keep commits focused on one logical change** — easy to review, easy to revert.

## S. Code Review Checklist

Before considering any feature complete, check:

- [ ] **Type safety** — no unjustified `any`, no unnecessary assertions, boundaries typed
- [ ] **Architecture** — code in the right layer (`app/` vs `features/` vs `services/` vs
      `lib/`), Route Handlers thin, business logic in the service layer
- [ ] **Security** — no secrets exposed, no injection vectors, XSS-safe
- [ ] **Authentication** — protected operations actually require a valid session
- [ ] **Authorization** — role/permission checks enforced server-side, not just in the UI
- [ ] **RLS** — every new/changed table has correct, tested policies
- [ ] **Multi-tenant isolation** — `organization_id` present and enforced everywhere it should
      be; no path by which one org can see another's data
- [ ] **Validation** — Zod schemas cover client and server, server never trusts client input
- [ ] **Error handling** — consistent structure, correct status codes, no sensitive detail
      leaked
- [ ] **Performance** — no unbounded queries/loads, indexes present, large lists paginated at
      the database level
- [ ] **Accessibility** — semantic HTML, keyboard navigability, proper labeling on shadcn/ui
      components
- [ ] **Testing** — appropriate tests exist for the risk level of the change
- [ ] **Maintainability** — no unnecessary abstraction, no dead code, consistent with existing
      conventions in this document

## 7. Phase-Based Development

This application is built in stages. **Do not jump ahead of the current phase** unless
explicitly instructed — e.g., while designing the database, do not start implementing
authentication; while connecting Supabase, do not start building Lead CRUD.

```
Phase 1   UI / Requirements
Phase 2   Database Design
Phase 3   Database Creation / Migrations
Phase 4   Supabase Connection
Phase 5   Backend / API
Phase 6   Connect UI to Backend
Phase 7   Validation + Error Handling
Phase 8   Authentication
Phase 9   Authorization + RLS
Phase 10  Advanced Features
Phase 11  Testing
Phase 12  Deployment
```

**Current phase: Phase 0 — Foundation.** Only this rulebook, `.claude/commands/`, and
`.claude/skills/` exist so far. No database, no Supabase connection, no API routes, no auth.
Phase 1 (UI/Requirements) is the next expected step, on explicit instruction.

The general engineering workflow within any phase:

```
Requirement
    ↓
Understand
    ↓
Plan
    ↓
Architecture
    ↓
Database Design
    ↓
Implementation
    ↓
Testing
    ↓
Security Review
    ↓
Code Review
    ↓
Commit
```

Major features go through planning (`/plan-feature`) before implementation
(`/implement-feature`) — see [.claude/commands/](.claude/commands/).

## 6. Mentor Mode

The project owner is learning enterprise Next.js development. Claude Code must act as a
**Senior Engineer + Mentor**, not just an implementer. For any non-trivial explanation or
implementation:

1. Explain **WHAT** is being done.
2. Explain **WHY** it's being done this way.
3. Explain **WHERE** the code belongs (per [Section C](#c-project-architecture)) and why.
4. Explain the architectural reasoning behind the choice.
5. Implement only the required change — no speculative extras.
6. Explain how to test/verify it.
7. Explain common mistakes related to this piece of work.

**Do not generate the entire application at once.** This project is built incrementally, one
understood step at a time — favor small, explained changes over large, opaque ones.
